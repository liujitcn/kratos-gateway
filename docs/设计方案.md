# kratos-gateway 设计方案

> 面向 kratos 体系（Go + kratos v3 + kratos-kit）的长期自研 API 网关。
> 本文档是项目的设计基线：目标、选型决策、架构模型、接口设计、演进路线。
> 状态：**v1.0 已实现**（2026-11-25，代码与测试见本仓库；v0.1–v1.0 各版特性全部落地）。定稿日期：2026-11-25。

---

## 1. 项目定位与背景

### 1.1 背景

kratos-admin 当前是**模块化单体**：`base / system / rag / bi / workflow` 等业务模块运行在同一个 `kratos-admin` 进程内，服务发现注册名为 `kratos-admin`（经 `NormalizeForRegistry` 规范化）。前端（admin 管理端 / uni-app 应用端）直连后端 HTTP 端口。

未来微服务拆分后，流量分两个方向，治理手段完全不同：

| 方向 | 含义 | 治理手段 |
|---|---|---|
| **东西向** | 服务 ↔ 服务（内部 RPC） | 服务间直接用 Consul discovery 客户端互调，**不经网关** |
| **南北向** | 前端 → 各服务（外部入口） | **本网关**：统一入口、按路由分发、流量治理 |

> 已实测：kratos v3 服务间 discovery 直连可行（`discovery:///服务名` + 负载均衡），详见第 6 节的规避项。

### 1.2 项目目标

1. **统一入口**：多服务按路由前缀分发到 Consul 中的不同服务，客户端无感知
2. **服务发现驱动**：实例列表实时来自注册中心（首版 Consul），实例上下线自动摘除/接管
3. **流量治理**：负载均衡 → 灰度权重 → 限流熔断，按版本演进逐步补齐
4. **体系一体**：与 kratos-kit 的 registry 工厂、config 配置体系、未来业务中间件同源设计，**拦截器不打架**

### 1.3 非目标（边界）

- **不做鉴权/会话**：认证授权留在服务侧（历史教训见 2.2），网关只做转发与传输层治理
- **不做业务语义加工**：脱敏、审计、i18n 等业务中间件归服务侧
- **不替代服务间 RPC**：东西向流量不经过网关

## 2. 选型决策记录（ADR）

### 2.1 候选方案对比

| 方案 | 结论 | 关键原因 |
|---|---|---|
| **nginx（+consul-template）** | 生产过渡可用，不满足长期 | 路由/发现配置手工维护；无 Filter 扩展模型；灰度/权重能力弱 |
| **APISIX / Kong** | 生产备选，未选 | 功能完备，但引入独立配置中心（etcd）与插件生态，与 kit 体系割裂 |
| **go-kratos/gateway** | **不引入** | kratos **v2** 血统、从未发过 release（只能源码构建）；中间件与 kit 全面撞车（见 2.2） |
| **Spring Cloud Gateway** | **不引入**（仅参考思想） | JVM 运行时，给 Go 技术栈增加整套 Java 运维成本 |
| **自研（本项目）** | **选定** | 与 kit registry 工厂/config 体系一体；网关过滤器与业务中间件同源设计，冲突天然消解；kratos v3 selector 可直接复用 |

### 2.2 go-kratos/gateway 拦截器冲突实证（2026-11-25 对照）

后端 HTTP 层已有中间件（`kratos-kit/server/http` + `kratos-core/server/http` + 应用层）：
`handlers.CORS`、Recovery、Tracing、Metadata、Logging（含 `base_api_log` 审计落库）、Validate、pprof、动态限流（`base_rate_limit_rule` / `base_api_rate_limit_policy`，DB 管理）、脱敏、authn/authz（会话 + casbin）。

与 go-kratos/gateway 中间件逐项对照：

| gateway 中间件 | 项目已有 | 判定 |
|---|---|---|
| cors | kit CORS（配置驱动） | 🔴 硬冲突：双层 `Access-Control-*` 头，浏览器直接报错 |
| auth | authn/authz（会话引擎 + casbin） | 🔴 语义冲突：JWT 模型 vs 项目会话体系 |
| ratelimit | DB 管理的动态限流 | 🔴 叠加冲突：提前 429，语义混乱 |
| logging | 访问日志 + 审计落库 | 🟡 双份冗余 |
| metrics / tracing | 已有 | 🟡 双份采集 / span 树 |
| datacenter | 单机房未使用 | ⚪ 无用 |
| （纯转发） | —— | ✅ 唯一不冲突部分——全关后等于重型 nginx |

**教训（设计铁律）**：网关过滤器与业务中间件必须**同一套体系、显式分层**——网关层只做传输与路由治理（匹配、负载均衡、灰度、限流、熔断），业务语义（鉴权、审计、脱敏、CORS）全部留在服务侧。

## 5. 核心模型接口设计

> 原则：Predicate/Filter 借鉴 SCG 抽象，转发/选择层直接复用 kratos v3 已验证接口；过滤器用标准 `http.Handler` 装饰链（而非自定义 middleware 签名），与 net/http 生态零摩擦。
> 以下接口签名中的外部类型均为真实存在（详见第 6 节来源）。

```go
// Route 一条转发规则：谓词全匹配命中后，经过滤器链转发到 target。
type Route struct {
    ID         string
    Predicates []Predicate   // 全部命中才匹配（AND）
    Filters    []Filter      // 路由级过滤器，按 Order 升序
    Target     Target        // 服务发现目标或静态地址
    Metadata   map[string]string // 预留：v0.3 服务自描述路由聚合原始元数据
}

// Predicate 请求匹配断言（借鉴 SCG）。
type Predicate interface {
    Match(r *http.Request) bool
}
// 首批实现：PathPredicate（段前缀 + 最长匹配，前缀树实现，语义见第 7 节）、
// MethodPredicate、HeaderPredicate、
// WeightPredicate（灰度：组内按权重分流，基于请求特征稳定哈希）。

// Filter 过滤器：装饰 next 构造处理链；Order 决定装配顺序。
type Filter interface {
    Order() int
    Do(next http.Handler) http.Handler
}
// 全局过滤器（日志/指标/恢复）与路由级过滤器共用此接口，全局链在前。
// 链尾是 ForwardHandler（非 Filter，不参与 Order）：调 Target.Select 拿节点后
// 交给 httputil.ReverseProxy 转发——过滤器链必须收敛到它。

// Target 转发目标：选出本次转发的节点（服务发现目标或静态地址）。
type Target interface {
    Select(ctx context.Context) (selector.Node, selector.DoneFunc, error)
}
// 首版两个实现：
//   DiscoveryTarget：service + scheme + lb 算法；节点表来自 UpstreamManager
//   StaticTarget：静态 URL 列表（联调/降级），自持 selector，构造时 Apply 一次

// UpstreamManager 按服务名、协议、算法和版本缓存 Watch、节点快照及熔断状态。
//   Watch 循环（6.3）发布节点快照，并更新手写路由使用的共享选择器。
//   自描述路由各有选择器，首次使用新快照时更新候选节点。
//   转发完成后必须调用 DoneFunc（喂 RTT/统计；p2c/ewma 的前提，v0.1 起固化）

// Selector 负载均衡：直接复用 kratos v3 接口（kratos/v3/selector，
// Selector 内嵌 Rebalancer，Apply 即接口方法，无需类型断言）。
//   Select(ctx, ...SelectOption) (Node, DoneFunc, error)
//   Apply(nodes []Node) —— 实例表变更时重灌
// 首版实现：
//   round_robin（自建，简单计数轮询，dev 场景足够）
//   wrr：直接复用 github.com/go-kratos/kratos/v3/selector/wrr.NewBuilder()
//        （nginx 平滑加权轮询；节点权重读 Metadata["weight"]，
//         selector.NewNode 已内建该解析，已对照 v3 源码确认）
```

`Target.Select` 直接返回选中的节点和完成回调。选择器通过 `Apply` 接收候选节点，通过 `Select` 为请求挑选节点。同一服务的自描述路由可能对应不同的候选节点，分别维护轮询状态可以保持各自的分流比例。

**为什么自建 Selector 而不用 kratos transport 的 balancer**：`transport/grpc` 的 `"selector"` balancer 存在 init 顺序缺陷（3 节），且无导出切换选项；而 `kratos/v3/selector` 包是纯接口 + 可独立复用的实现（wrr/p2c），零 transport 依赖——复用它的接口与实现，既规避缺陷又不重复造轮子。

## 6. 服务发现集成（探查实证，2026-11-25）

### 6.1 依赖组合（最小集）

| 包 | 用途 |
|---|---|
| `go-kratos/kratos/v3/registry` | 仅接口（`Discovery/Watcher/ServiceInstance`），零实现依赖 |
| `liujitcn/kratos-kit/api/gen/go/config/v1` | `configv1.Registry` / `Registry_Consul` 配置结构 |
| `liujitcn/kratos-kit/registry` | `NormalizeForRegistry` 服务名规范化和注册中心工厂 |
| `liujitcn/kratos-kit/registry/consul` | 网关自注册、心跳和注销 |
| `hashicorp/consul/api` | 健康实例阻塞查询和目录查询 |
| 可选 `kratos/v3/selector` + `selector/wrr` + `selector/node/direct` | 负载均衡接口与实现 |

> **约束**：不引入任何 `kratos/v3/transport` 子包（规避 balancer init 缺陷）；`selector`、`wrr`、kit consul 包均已验证无 transport 依赖。

### 6.2 接入方式

网关使用 Consul API 查询健康实例。注册和注销使用 Admin 同一条 Kratos bootstrap 生命周期与 kit 注册器。Kratos 在注册前绑定地址，使用实际监听端口注册。Consul TCP 健康检查由 `registry.consul.health_check` 启用。

配置结构直接复用 `configv1.Registry`——与 kratos-admin 的 `configs/*/registry.yaml` **完全同构**（type/consul.address/consul.scheme/consul.token/consul.health_check），未来换 etcd/nacos 只换 type。

### 6.3 实例同步循环

```go
// 首条路由启动订阅，服务名、协议、算法、版本相同的路由共享订阅
name := kitreg.NormalizeForRegistry(appID, "consul") // 服务名规范化，必须与注册方一致
w, _ := disc.Watch(ctx, name)
for {
    ins, err := w.Next()                              // Consul 健康查询，后续阻塞等待索引变更
    if err != nil { /* 保留旧快照并退避 */ continue }
    nodes := buildNodes(ins)                          // selector.NewNode(scheme, addr, in)
    sel.Apply(nodes)                                  // Selector 内嵌 Rebalancer，实例表变更重灌
}
```

### 6.4 关键规则（违反即查不到/连不上）

1. **服务名规范化**：`NormalizeForRegistry` 对 consul 做 小写化、`_` 等非字母数字合并为单个 `-`、去首尾 `-`、最长 **64 rune**、空则回退 `"service"`。网关查询与注册方必须用同一规则，否则 Watch 查不到服务。
2. **Endpoints 按 scheme 分流**。发现客户端从 Consul tagged addresses 读取注册时写入的完整地址，跳过 LAN/WAN 专用地址。网关按路由配置选择 `http` 或 `https`。
3. **健康过滤**使用 `Health().Service(..., passingOnly=true)`。查询失败时保留最近一次成功的快照，成功返回空列表时清空节点。
4. **ACL**：Consul 开 ACL（`default_policy=deny`）时 token 必填，匿名注册/读均 403。token 管理约定见第 11 节。

## 7. 路由配置模型（YAML 示例）

共享 bootstrap 从 `-c` 指定的目录加载基础配置，并用 `-e` 对应的文件覆盖同名字段。`gateway` 作为扩展配置注册，解码时拒绝未知字段。过滤器的 `args` 由对应过滤器解释。首次装配失败时网关在监听前退出。服务发现的首个快照可异步发布。

本地配置轮询只发布静态路由变化。解析或装配失败时使用旧路由表。有生效路由时，热更新新增的上游池须收到首个成功的发现快照，允许为空。等待期间旧路由和订阅继续服务。HTTP、注册中心、目录参数和启用远程配置时的路由改动在重启后生效。

路由 ID 唯一且限流过滤器的顺序、速率和桶容量相同时，热更新保留已有令牌桶。服务名、协议、负载均衡算法、版本相同的路由共享熔断参数。省略 `breaker` 的路由继承同池显式参数，整个池省略时采用默认值。显式参数冲突时拒绝装配。新参数随候选路由表生效，保留池内的失败计数和冷却起点。

```yaml
# server.yaml
server:
  http:
    addr: :8080
    middleware:
      enable_recovery: true

# registry.yaml
registry:
  type: consul
  consul:
    health_check: true

# gateway.yaml
gateway:
  routes:
    - id: admin-api
      predicates:
        - path: /api/v1/base
      target:
        service: kratos-admin
        scheme: http
        lb: round_robin
```

**路由匹配规则（Router 装配前必须实现）**：

1. **段前缀语义**：`path: /api/v1/base` 命中 `/api/v1/base`（自身）与 `/api/v1/base/任意子路径`，**不命中** `/api/v1/base2`——按路径段对齐，防止字符串前缀误伤（`/api/v1/base` 误配 `/api/v1/base64` 这类事故必须在语义层杜绝）。不引入 Ant 风格 `**` 通配（与"前缀匹配"语义混淆，v0.2 若需精确/多段匹配再扩展 PathPredicate 语法并独立定义）
2. **最长前缀优先**：多条路由前缀重叠（如 `/api/v1` 与 `/api/v1/base`）时，段数更多者胜；同段数按配置声明顺序，先声明者胜
3. **未命中返回 404**（响应体标注 `gateway: no route` 便于排障）
4. **灰度分流**使用组内一致的哈希键，权重之和必须为 100。

> v0.3 起支持**服务自描述路由**。实例在 Consul 注册元数据中声明自己的 path 前缀（如 `gateway_routes=/api/v1/bi`，多前缀以逗号分隔）。目录按 `catalog.service_prefixes` 筛选服务名，再查询健康实例。网关聚合实例声明生成路由，每条路由只转发给声明对应前缀的健康实例。路由与负载均衡分别通过 `gateway_routes` 和 `gateway_lb` 声明。

## 8. 转发与流式（2026-11-25 实测固化为规范）

| 项 | 规范 | 依据 |
|---|---|---|
| SSE/流式透传 | `FlushInterval = -1` **全局统一设置**，无需按路由配置 filter（对普通小响应仅增加即时 flush，开销可忽略） | dev LB 代理实测 `/events` 透传正常 |
| 超时边界 | 入站 `ReadHeaderTimeout=10s`、`IdleTimeout=120s`，上游 `ResponseHeaderTimeout=30s` | 上游期限只覆盖等待响应头的阶段。SSE/WS 建连后继续流式传输 |
| 无健康实例 | 返回 `503 no healthy instance`，带重试语义的客户端可退避 | 实测行为 |
| 实例刷新 | Consul 健康查询阻塞等待索引变化 | 查询失败后退避 1 秒重试 |
| Host 头 | `pr.SetXForwarded()` + 保留原始 Host | 实测 |
| WebSocket | `ReverseProxy` 原生支持 upgrade。`response-header` 可覆盖 `101` 响应的同名头 | 与普通 HTTP 请求共用排空期限，到期后强制断开 |
| 转发完成回调 | 每笔转发结束必须调用 `DoneFunc`（上报 `DoneInfo{Err}`）——命中统计与未来 p2c/ewma 的 RTT 输入 | kratos selector 接口约定 |
| 重试与熔断 | `max_retry` 为非负数。安全方法在请求体为空或可重放时可换节点重试。半开节点收到 HTTP 响应头或成功接管升级连接后即可恢复接流量 | 失败计数反映上游传输故障。客户端取消或路由期限到期时只释放半开探测资格 |

**已知限制（v0.1–v0.3）**：实例健康完全依赖 Consul——进程崩溃后须等 TTL 过期才被标记 critical 摘除，存在分钟级误发窗口；主动失败摘除与被动熔断排在 v0.4（对幂等 GET 的连接类错误重选重试也在 v0.4）。

## 9. 可观测性

1. **`X-GW-Upstream` 响应头**：每笔响应标注实际命中的 `host:port`——浏览器 DevTools / 网关测试直接可见流量分布（dev LB 代理已验证该模式）
2. **`/gw-stats` 统计端点**默认关闭，设置 `gateway.server.stats: true` 可启用。返回的 JSON 包含当前路由表、各上游实例的累计命中数和健康实例列表。
3. **结构化访问日志**：`method path -> upstream 状态 耗时`，格式对齐 kit 日志规范
4. **Prometheus metrics**（v1.0）记录请求计数和耗时，扩展 HTTP 方法统一使用 `OTHER` 标签。
5. **接流探针 `/readyz`** 在启用目录时等待首次成功发布目录快照，允许空目录。每条已发布的发现路由都须有至少一个匹配节点，按当前发现快照判断。静态目标不额外探测。收到停机信号时，Kratos 注销实例，随后网关将探针切换为 `503` 并排空连接。`/healthz` 供独立的存活检查使用。容器和负载均衡器使用 `/readyz` 检查接流状态。滚动部署先摘除待停实例并等待负载均衡生效，再停止实例。新实例 `/readyz` 返回 `200` 后恢复接流。

## 11. 与 kratos-admin 的协作约定

1. **注册元数据规范**包括 `gateway_routes`（path 前缀列表）、`gateway_lb`（`round_robin` 或 `wrr`，缺省为 `round_robin`）、`weight`（wrr 实例权重）和 `version`（供 `target.version` 筛选实例）。自描述路由跳过声明无效算法的实例。未填写 `version` 元数据的旧实例仍可按注册版本匹配。
2. **鉴权边界**：网关不做认证授权（2.2 教训）；服务侧 authn/authz 中间件保持现行为，网关透传原始请求头
3. **SSE 跨实例共享**（多实例前置待验证项）。`/events` 事件广播与登录态是否走 Redis pub/sub 共享，决定多实例部署下客户端连不同实例是否等价。开启 `target.sticky` 后，同一客户端连接按上游池固定节点。
4. **Consul ACL**：60.83 Consul 已开 ACL（`default_policy=deny`），bootstrap 管理 token 已签发（2026-11-25）；网关与业务服务的 registry token 应收敛为**独立的服务读写专用 token**（`service:read`/`service:write` 最小权限），不直接复用 management token
5. **验证账号与环境**：dev 环境 Consul `192.168.60.83:8500`；kratos-admin 免认证验证路由 `GET /api/v1/base/captcha`；7001/6001 为日常开发实例勿占用
